# Save gaps

Fixes for the "Save/load gaps" in CODECHECK-A / CODECHECK-B. Code: `Assets/Groundbreak/Scripts/SaveGaps/`,
tests: `Assets/Groundbreak/Tests/SaveGapTests.cs` (round 1), `Assets/Groundbreak/Tests/SaveGaps2Tests.cs` (round 2) and
`Assets/Groundbreak/Tests/SaveGaps3Tests.cs` (round 3).

## Now saved

Sections load in ascending order (`SaveSystem.RegisterExtension(key, save, load, order)`, default 0; ties keep registration order).

`SaveSystem.Version` is 3 (round 3 only adds sections and an optional `ToolData.state`, so no bump). Version-1, -2 and round-2 version-3 files load unchanged: a missing section loads as empty (the session's objects
for it are cleared, nothing is restored). Old files written before a piece filter existed still carry those pieces as plain pieces
(e.g. form boards or roof trusses from a v2 save come back as plain boards, as they did before).

## Adding a save section

1. In your feature folder, register once from `BeforeSceneLoad`:
   `SaveSystem.RegisterExtension("mykey", Save, Load);` (or with an order: negative = before the rest).
2. `Save()` returns JSON (`JsonUtility` on a `[Serializable]` DTO; never null-able nested classes, use has-flags).
3. `Load(json)` first clears the feature's runtime objects (deactivate + destroy, and clear static lists right away), then
   returns if `json` is null (old save or New Game) or rebuilds from the DTO. It runs after pieces, stock and belt are restored.
4. State that hangs off a piece: refer to it with `SaveGaps.Ref(piece)` and find it with `new SaveGaps.PieceIndex().Find(ref)`.
   State that hangs off a framing face: `SaveGaps.Plane(fp)` / `SaveGaps.FindPlane(ref)`.
5. Pieces your feature rebuilds itself: `SaveSystem.RegisterPieceFilter("mykey", p => p.GetComponent<MyPart>() != null)`.
6. Needs another section loaded first? Give it a later order, or do that part in `SaveSystem.AfterLoad` (see `SlabSave`).
7. Rebuild steps that toast: wrap in `SaveGaps.Quiet(...)`; replays through a trade API that takes stock / tools / scrap:
   `SaveGaps.Replay(() => ..., toolIds)`. A `FramingJob` is replayed with `job.ReplayTo(next)`.
8. A builder that makes `FramingJob`s outside the shell: call `JobRecipe.Attach(job, "kind", pos, yaw, supportTransform, args...)`
   when planning and `JobSave.RegisterKind("kind", recipe => Plan(...))` once; the "jobs" section saves and replays it.
9. A tool with consumable / loaded state: a public field on the tool class is saved automatically; private state: implement
   `ISavedToolState`.

## Still not saved (player-placed or player-made)

- Contractor-site houses (`ContractorJobSite`) rebuild themselves; other framing jobs made without a `JobRecipe` (none known in
  the game today) come back as plain pieces (roles kept by `leftovers`). A new builder can opt in with `JobRecipe.Attach` +
  `JobSave.RegisterKind`.
- Shell / stair pieces the player moved after the job come back where they were, but as plain pieces (no cut shape / role).
- Stair-builder jobs from a round-2 (version-3) save: their pieces were saved as plain pieces then and still come back that way
  (their stringers as cut stringers with seat boxes).
- A form outline being drawn comes back without its undo history beyond the corners themselves (undo still removes corners).
  A ready-mix truck that was already leaving when saved is gone on load (the order is finished; nothing is owed either way).
- `ElLoad` box mounting (recomputed on demand).
- A set slab that wasn't poured in saved forms (one restored from a version-2 save, or made without `FormSystem`) still comes back
  through `slabs` without a `PourSystem` behind it (can't be finished again; landscaping treats it as plain ground). Its cure
  colour does update.
- Tool state kept in private fields of tools that don't implement `ISavedToolState` (none hold consumables today: the
  insulation blower's part bag lives on the attic and is saved there).
